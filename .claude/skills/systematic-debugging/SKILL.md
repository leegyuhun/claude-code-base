# Systematic Debugging

## 핵심 원칙

임의 수정은 시간을 낭비하고 새 버그를 만든다. 빠른 패치는 근본 문제를 감춘다.

**증상 수정은 실패다. 항상 근본 원인부터 찾아라.**

이 과정의 문자를 어기면 정신도 어기는 것이다.

## 절대 법칙

```
근본 원인 조사 없이는 어떤 수정도 제안할 수 없다.
Phase 1을 완료하지 않았다면 수정을 제안할 수 없다.
```

## 적용 시점

**모든 기술적 문제에 사용:**
- 컴파일 오류 (빌드 실패)
- 런타임 예외
- 예상과 다른 동작
- DB 쿼리 결과 오류
- UI 렌더링 이상
- 성능 문제

**특히 다음 상황에서 반드시 사용:**
- 시간 압박 상황 (긴급할수록 즉흥 패치 충동이 강해짐)
- "이것만 바꾸면 될 것 같다"는 느낌이 들 때
- 이미 여러 번 수정을 시도했을 때
- 이전 수정이 통하지 않았을 때

**건너뛰지 말 것:**
- 문제가 단순해 보일 때 (단순한 버그에도 근본 원인이 있다)
- 급할 때 (체계적 접근이 즉흥 패치보다 빠르다)

## 4단계 절차

각 단계를 완료한 후에만 다음 단계로 진행한다.

### Phase 1: 근본 원인 조사

**수정 시도 전 반드시 완료:**

1. **오류 메시지 완전히 읽기**
   - Delphi 컴파일 오류: 파일명, 줄 번호, 오류 코드 기록
   - 런타임 예외: EAccessViolation·EInOutError 등 예외 유형 확인
   - build.bat 출력 전체 확인 (첫 오류만 보지 말 것)

2. **재현 확인**
   - 동일한 조건으로 반복 발생하는가?
   - 어떤 순서로 실행했을 때 발생하는가?
   - 재현 불가 시 → 추측 금지, 더 많은 데이터 수집

3. **최근 변경 확인**
   - `git diff HEAD` — 이번 스프린트 변경 사항
   - `git log --oneline -10` — 최근 커밋 이력
   - 어떤 변경이 이 증상을 유발했는가?

4. **YSR 빈출 버그 진단 체크리스트**

   | 증상 | 가능한 원인 | 진단 방법 |
   |------|-------------|-----------|
   | 컴파일 오류 (CP949 관련) | Write 도구로 .pas 저장 → UTF-8 변환 | `python3 -c "data=open('파일.pas','rb').read(3); print(data.hex())"` → `efbbbf`이면 BOM 손상 |
   | EAccessViolation | nil 포인터 역참조, Free 후 접근 | nil 체크 위치 및 FreeAndNil 미사용 확인 |
   | TDataSet 상태 오류 | State 미확인 후 Post/Close | `if ADataSet.State in [dsEdit, dsInsert] then` 누락 |
   | SQL 오류 (Sybase) | PG 전용 문법 사용 | `UsingPg` 분기 누락 확인 |
   | GDI 핸들 누수 | DeleteObject 미호출 | SelectObject 복원 + DeleteObject 쌍 확인 |
   | 메모리 누수 | try..finally 누락 | Create/Free 쌍, FreeAndNil 사용 여부 확인 |
   | 한글 깨짐 | AnsiString/WideString 혼용 | 변환 지점 확인 |
   | 멀티컴포넌트 오류 | 컴포넌트 경계 데이터 흐름 불명확 | 각 경계에서 입출력값 로깅 |

5. **멀티컴포넌트 경계 진단 (복합 문제 시)**
   - 각 컴포넌트 경계(폼↔데이터모듈, 데이터모듈↔DB)에서 입출력값 로깅
   - WriteLogMan이나 TLogger.BeginTask/EndTask 활용
   - 어느 경계에서 값이 잘못되는지 확인 후 그 컴포넌트만 조사

6. **데이터 흐름 추적**
   - 잘못된 값이 어디서 시작되었는가?
   - 콜 스택을 역방향으로 추적 (`root-cause-tracing.md` 참조)
   - 증상 위치가 아니라 원인 위치에서 수정

### Phase 2: 패턴 분석

**수정 전 패턴 확인:**

1. **동작하는 예시 찾기**
   - 동일 코드베이스에서 유사하게 동작하는 코드 찾기
   - 작동하는 것과 깨진 것의 차이점은?

2. **레퍼런스 완전히 읽기**
   - `.claude/rules/delphi2007-patterns.md` 해당 섹션 전체 확인
   - 스킵 금지 — 모든 줄을 읽어야 패턴을 올바르게 적용할 수 있다

3. **차이점 식별**
   - 작동하는 코드와 깨진 코드의 차이를 모두 나열
   - "그건 중요하지 않을 것" 가정 금지

### Phase 3: 가설 및 검증

**과학적 방법론:**

1. **단일 가설 수립**
   - "X가 근본 원인이다. 왜냐하면 Y이기 때문이다"
   - 명확하게 적는다
   - 모호하게 쓰지 않는다

2. **최소한의 변경으로 검증**
   - 가설을 검증하는 가장 작은 변경만 한다
   - 한 번에 하나씩
   - 여러 수정 동시 적용 금지

3. **결과 확인**
   - 동작: Phase 4로 진행
   - 미동작: **새 가설 수립** (기존 수정 위에 더 쌓지 말 것)

4. **모를 때**
   - "X를 이해하지 못하겠다"고 말할 것
   - 아는 척 금지
   - 추가 조사 후 진행

### Phase 4: 구현

**증상이 아닌 근본 원인을 수정:**

1. **수정 전 재현 테스트 작성** (또는 재현 경로 기록)
2. **단일 수정** — 근본 원인만. "하는 김에" 개선 금지
3. **수정 검증** — build.bat 실행 후 재현 경로 확인
4. **수정이 안 되면?**
   - 즉시 중단
   - 시도 횟수 세기
   - 3회 미만: Phase 1로 돌아가 새 정보로 재분석
   - **3회 이상: STOP — 아키텍처 문제 가능성, 사용자에게 보고**
   - 4번째 수정 시도 금지

## 경보 신호 — 즉시 중단

다음 생각이 드는 순간 멈추고 Phase 1로:
- "이 부분을 바꿔보면 될 것 같다"
- "아마 X 때문일 것이다, 바꿔보자"
- "여러 곳을 동시에 고쳐보자"
- "테스트 결과 확인 없이 진행"
- "원인을 완전히 이해하지 못하지만 시도해보자"
- **"한 번만 더 시도" (이미 2번 이상 실패했을 때)**
- **각 수정마다 다른 위치에서 새 문제 발생**

**마지막 두 개: STOP. 아키텍처 문제. 사용자에게 보고.**

## 합리화 방지

| 핑계 | 현실 |
|------|------|
| "단순한 버그라 절차 불필요" | 단순 버그도 근본 원인이 있다. 절차가 오히려 빠르다. |
| "긴급 상황이라 시간 없다" | 체계적 접근이 즉흥 패치보다 빠르다. |
| "일단 시도하고 조사하자" | 첫 시도가 패턴을 만든다. 처음부터 올바르게. |
| "참조 문서가 너무 길다" | 부분 이해는 버그를 보장한다. 전체를 읽어라. |
| "원인을 봤으니 바로 고치자" | 증상을 봤다 ≠ 근본 원인을 이해했다. |
| "또 한 번만 시도" (3번 실패 후) | 3번 실패 = 아키텍처 문제. 계속 시도 금지. |

## 보조 기법

이 디렉토리의 보조 파일:
- **`root-cause-tracing.md`** — 콜 체인을 역방향으로 추적해 원래 트리거 찾기 (Delphi 맥락)
- **`condition-based-waiting.md`** — 임의 Sleep 대신 실제 조건 대기로 flaky 문제 제거

## 실제 효과

체계적 접근: 15~30분 내 해결
즉흥 패치 반복: 2~3시간 소비
첫 번째 수정 성공률: 체계적 95% vs 즉흥 40%
신규 버그 유발: 체계적 거의 없음 vs 즉흥 빈번
