# PRD 문서 템플릿

> `/prd` 커맨드 Phase 3에서 이 파일을 읽어 PRD.md를 생성한다.
> 섹션 순서와 변수 자리표시자(`{...}`)를 유지하고, 실제 값으로 치환하여 저장한다.

---

## 작성 원칙

- 각 섹션은 구체적이고 검증 가능하게 작성
- "검증 계약 (MVP)"는 Validator PHASE 7의 채점 대상이다. Defect 트랙에서는 PRD가 GOAL.md를 대체하므로 자동(빌드·테스트)과 수동(UI) 항목을 명확히 구분하여 작성
- 우선순위(P0/P1/P2)는 orchestrator의 plan.md 기능 목록과 직결되므로 반드시 분류
- 사용자가 "모른다"고 한 항목은 "[확인 필요]"로 표기
- `ADDITIONAL_CONTEXT`가 있으면 "목적 & 배경"에 이슈 설명과 자연스럽게 통합 서술하고,
  "관련 레퍼런스" 섹션에 `**사용자 보완 메모:**` 항목으로 원문을 부속 기록(추적성 확보)
- "재현방법" 섹션은 **버그/이슈 기반 PRD에서만** 작성. 신규 기능 PRD면 섹션 전체를 생략한다.
  - Redmine 이슈가 있거나 `EXTRA_CONTEXT`에 버그/오류/재현 관련 키워드가 있으면 자동 포함
  - 재현 단계는 번호 매긴 순서대로, "기대 결과"와 "실제 결과"를 분리 기술
- **원인 분석 시 필수 검증** (버그/이슈 기반 PRD)
  - **수치 증거가 있으면 산식 역산 필수**: 기대값/실제값 두 수치를 후보 산식으로 직접 계산해 어느 산식이 어느 값을 만드는지 확정한 뒤에야 root cause를 짚는다. 가설로만 두지 말 것.
  - **"분기 존재 ≠ 정상 동작"**: 차등환자·예외 처리 같은 `if` 블록이 보인다고 정상으로 단정하지 말 것. 분기 내부 산식 자체가 틀려 있을 수 있음. 분기가 있어도 산식 검증을 별도로 수행한다.
  - **최근 추가된 코드 우선 의심**: 회귀 버그는 새로 추가된 분기/필드/플래그가 원인일 확률이 가장 높다. git log/blame으로 최근 변경 이력을 확인하고, 신규 코드를 신뢰 기준이 아니라 1차 의심 대상으로 둘 것.
  - **증상 보고는 현상이지 진단이 아님**: "A 경로는 정상, B 경로만 오류" 같은 사용자 보고를 진단의 전제로 받아들이지 말 것. "두 경로가 정말 다른 코드를 타는가" 자체를 의심해야 한다.

## 재현방법

> 이슈/버그를 재현하기 위한 절차. Validator가 수정 전후 검증 시나리오로 사용한다.

**사전 조건:**
- {환경·권한·데이터 상태 등 재현 전 필요한 조건}

**재현 단계:**
1. {단계 1 — 구체적 동작}
2. {단계 2}
3. {단계 3}

**기대 결과:** {정상 동작 시 보여야 할 결과}

**실제 결과:** {현재 관찰되는 잘못된 결과 — 오류 메시지·스크린샷 경로 등}

**재현 빈도:** 항상 / 간헐적({조건}) / 특정 환경만({환경})

{기대값/실제값이 **수치**인 경우 (금액·수량·날짜 등) — 산식 역산 결과를 반드시 기재한다.
**산식 역산 (수치 증거 검증):**
- 기대값 {N}을 만드는 산식: {예: `bhTotJinryo × 30% = N`}
- 실제값 {M}을 만드는 산식: {예: `(bhTotJinryo - 선별급여) × 30% + 선별급여 × 90% = M`}
- → 어느 코드 위치의 어떤 산식이 실제값 산출 경로와 일치하는가: {파일:라인}
}

---
